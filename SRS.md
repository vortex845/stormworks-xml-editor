Проект: Stormworks XML Editor
Стандарт: ISO/IEC/IEEE 29148:2018
Версия: 1.0
Дата: 02.11.2026

## 1. Введение

### 1.1 Назначение
Целью данного документа является определение требований к десктопному приложению для ОС Windows, предназначенному для просмотра и редактирования файлов построек (vehicles) игры *Stormworks*. Приложение позволяет пользователям изменять параметры объектов без необходимости запуска игры или ручного редактирования XML-кода.

Техническая реализация: приложение разрабатывается как настольное GUI-приложение на Python 3.11+ с использованием фреймворка PySide6 (Qt 6). GUI строится на основе QMainWindow, QWidget, QStackedWidget, и QSS-стилизации. Взаимодействие с файловой системой — через QFileDialog и модули os, glob. Парсинг XML — через xml.etree.ElementTree / lxml.

### 1.2 Границы проекта
Разрабатываемое ПО представляет собой автономное приложение.
*   Входит в границы проекта: Парсинг XML-файлов Stormworks, визуализация структуры постройки (список), редактирование компонентов (поворот, изменение размера объектов), сохранение изменений обратно в XML.
*   Не входит в границы проекта: 3D-рендеринг постройки в реальном времени, синхронизация с игрой по сети, создание новых компонентов с нуля (только на основе существующих ID игры).

Техническая реализация: автономность обеспечивается отсутствием сетевых модулей в зависимостях. Все операции выполняются локально над файлами в файловой системе пользователя. 3D-рендеринг не подключается (модули Qt3D/OpenGL не используются). Новые компоненты не создаются — редактор работает только с уже существующими записями XML.

### 1.3 Определения
*   SRS: Software Requirements Specification.
*   XML: Extensible Markup Language — формат файлов сохранений игры.
*   Component: Игровой блок или деталь.
*   GUI: Graphical User Interface — графический пользовательский интерфейс.

Техническая реализация: компоненты в коде представляются структурами Python с полями: id, name, x, y, z, rotation matrix (r), scale (sc), parent_path. XML-документ загружается в дерево ElementTree (или lxml.etree) и сохраняется обратно с сохранением порядка атрибутов.

### 1.4 Ссылки
*   ISO/IEC/IEEE 29148:2018.
*   Документация формата сохранений Stormworks ([Community Wiki](https://stormworks.fandom.com/wiki/Stormworks_Build_and_Rescue_Wiki)).
*   Microsoft Windows UI Guidelines.

Техническая реализация: документация Stormworks используется для сопоставления id компонентов с человекочитаемыми названиями. UI-гайдлайны Windows соблюдаются за счёт использования стандартных Qt-виджетов и нативных диалогов (QFileDialog.getExistingDirectory с флагом DontUseNativeDialog для корректного поведения поверх frameless-окна).

### 1.5 Обзор документа
Документ описывает общую концепцию продукта (Раздел 2), детальные функциональные и нефункциональные требования (Раздел 3), методы верификации (Раздел 4) и приложения (Раздел 5).

## 2. Общее описание

### 2.1 Перспектива продукта
Приложение является вспомогательным инструментом (третья сторона) для игры *Stormworks*. Оно решает проблему неудобства ручного редактирования XML-файлов, которые имеют сложную структуру и высокую вложенность. Приложение выступает в роли "просмотрщика и редактора свойств".

Техническая реализация:
*   Просмотрщик: XML загружается в ElementTree, обходится рекурсивно, компоненты извлекаются в плоский список (list[dict]), который отображается в QListWidget / QTreeWidget.
*   Редактор свойств: для выбранного компонента открывается панель с QLineEdit/QDoubleSpinBox, значения валидируются, изменения записываются обратно в соответствующий XML-узел.
*   UI: стилизация через main.qss, frameless-окно с кастомной шапкой (titleBar), боковой панелью (sideBar) и контейнерами с тенями.

### 2.2 Основные функции
*   Открытие и валидация XML-файлов сохранений Stormworks.
*   Отображение иерархической структуры постройки.
*   Поиск и фильтрация компонентов по типу или ID.
*   Редактирование свойств выбранных компонентов (поворот, изменение размера текстур объектов).
*   Экспорт измененных данных в валидный XML-файл.

Техническая реализация:
*   Открытие/валидация: QFileDialog.getExistingDirectory(...) → glob.glob(os.path.join(folder, "*.xml")) → xml.etree.ElementTree.parse(...) с обработкой ParseError.
*   Иерархия: QTreeWidget с колонками ID, Name, Type, заполняется рекурсивным обходом <bodies> → <body> → <components> → <c> → <o>.
*   Поиск/фильтрация: QLineEdit + фильтр QSortFilterProxyModel, либо фильтрация элементов списка по подстроке.
*   Редактирование: панель QFormLayout с полями QLineEdit (матрица r), QDoubleSpinBox (координаты), QSpinBox (масштаб sc).
*   Экспорт: обновление атрибутов в XML-дереве + tree.write(file, encoding="UTF-8", xml_declaration=True) с сохранением порядка атрибутов (при использовании lxml — parser=etree.XMLParser(remove_blank_text=False)).

### 2.3 Характеристики пользователей
Целевой пользователь — игрок в *Stormworks*, знакомый с основами механики игры, но не обязательно являющийся программистом. Пользователь ожидает интуитивный GUI.

Техническая реализация: интерфейс построен на стандартных паттернах (кнопки «Открыть папку», список файлов, панель свойств) с подсказками (setToolTip) и локализацией (русский/английский через словарь TEXTS). Сообщения об ошибках — через QMessageBox с понятным текстом (например, «В этой папке нет XML-файлов»). Отсутствие необходимости знать синтаксис XML.

### 2.4 Ограничения
*   ОС: Microsoft Windows 10/11.
*   Среда разработки: Язык программирования Python (Qt).
*   Формат данных: Строгое соответствие схеме XML игры Stormworks.

Техническая реализация:
*   Windows-only функции: ctypes.windll.shell32.SetCurrentProcessExplicitAppUserModelID(...) для корректной иконки на панели задач; работа с .ico-иконками.
*   Python + Qt: PySide6 (Qt 6), Python 3.11+.
*   Соответствие схеме: парсер не изменяет теги/атрибуты, не переставляет узлы; сохраняются data_version, bodies_id, порядок <authors>, <bodies>, <logic_node_links>. Валидация проводится по базовой структуре (vehicle → bodies → body → components → c → o).

### 2.5 Допущения и зависимости
*   Формат XML-файлов игры не изменится критически в ближайших обновлениях.
*   Пользователь имеет установленную игру для тестирования результатов редактирования.

Техническая реализация: парсер использует «мягкую» схему — неизвестные теги сохраняются как есть (FR-02). Если формат изменится, приложение продолжит работать, но может не распознать новые поля. Тестирование сохранённых файлов — через загрузку в Stormworks (см. FR-06). Зависимости проекта: PySide6, lxml (опционально), Pillow (для конвертации иконок).

## 3. Специфические требования

### 3.1 Внешние интерфейсы
*   User Interface: Графический интерфейс Windows (окна, панели инструментов, древовидные списки, поля ввода).
*   Software Interface: Файловая система Windows (чтение/запись .xml).
*   Hardware Interface: Не требуется специфического оборудования (работает на стандартном ПК).

Техническая реализация:
*   UI: QMainWindow (frameless), titleBar с кнопками btnClose/btnMinimize/btnInfo/btnGithub/btnLanguage, sideBar (навигация), QStackedWidget (домашняя/редактор), QListWidget (файлы), панель свойств (QFormLayout), кастомные тени через QGraphicsDropShadowEffect.
*   Software Interface: QFileDialog.getExistingDirectory(...), open(), os.path, glob, ElementTree.write(). Пути — относительные (assets/...) и абсолютные (выбранная пользователем папка).
*   Hardware Interface: стандартный ПК (x86_64, 4 ГБ RAM, интегрированная графика). Спец. оборудование не требуется.

### 3.2 Функциональные требования
| ID Требования | Описание требования |
| :--- | :--- |
| FR-01 | Загрузка файла. Система должна позволять пользователю выбирать XML-файл постройки через диалоговое окно. |
| FR-02 | Парсинг. Система должна считывать данные о компонентах, игнорируя неизвестные теги без вылета. |
| FR-03 | Визуализация. Система должна отображать список компонентов с возможностью сортировки по ID и названию. |
| FR-04 | Редактирование свойств. При выборе компонента система должна отображать его текущие параметры (например, x, y, z) в полях ввода. |
| FR-05 | Валидация ввода. При изменении параметров система должна проверять их на соответствие допустимым диапазонам. Дополнительно: Система должна предупреждать пользователя, если ID блока не найден в базе данных игры. |
| FR-06 | Сохранение. Система должна сохранять изменения в файл, сохраняя структуру оригинального XML (порядок тегов, атрибуты). |

### 3.3 Нефункциональные требования
| ID Требования | Описание требования |
| :--- | :--- |
| NFR-01 | Загрузка файлов большого объема. Система должна оставаться работоспособной при открытии файлов с более чем 1000 компонентов. |
| NFR-02 | Приложение не должно передавать данные в интернет. |

### 3.4 Ограничения проектирования
*   Приложение должно использовать нативные библиотеки Windows для обеспечения высокой скорости работы.

## 5. Приложения

### 5.1 Пример структуры XML для одного объекта 
```xml
<?xml version="1.0" encoding="UTF-8"?>
<vehicle data_version="3" bodies_id="2">
  <authors/>
  <bodies>
    <body unique_id="2">
      <components>
        <c>
          <o r="1,0,0,0,1,0,0,0,1" sc="6"/>
        </c>
      </components>
    </body>
  </bodies>
  <logic_node_links/>
</vehicle>
```
Техническая реализация: при парсинге:
*   root.tag == "vehicle", root.attrib == {"data_version": "3", "bodies_id": "2"}.
*   body = root.find("bodies/body"), body.attrib["unique_id"] == "2".
*   obj = body.find("components/c/o"), obj.attrib["r"] == "1,0,0,0,1,0,0,0,1", obj.attrib["sc"] == "6".
*   При сохранении атрибуты r и sc записываются обратно в том же порядке (ElementTree сохраняет порядок атрибутов с Python 3.8+; lxml — всегда).
